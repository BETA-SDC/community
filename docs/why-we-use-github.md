# Why We Use GitHub

欢迎大家来到 GitHub 的世界。

对于新人来说，第一次看到 GitHub，可能会觉得它有点“程序员风格”，甚至不太亲切。这个感受很正常。不过如果把它放到团队协作这个场景里看，你会发现它并不只是一个写代码的平台，更像是一个适合长期沉淀文档、追踪变化、共享信息的协作底座。下面我想用三个原因，解释我们为什么最终选择它。

#### 第一，我们要的是“极简共享”，不是“花哨孤岛”

我们团队在选择协作工具时，最核心的需求其实很朴素：

> **界面简单（至少基础功能要简单），展示和分享方便，用来记录进度、追踪任务、查阅历史文档。**

但我们试过不少第三方平台后发现，它们几乎都有一个通病：**内容被锁在自己的专属格式里**。

- 你在 A 平台写的东西，导出后别人不一定能顺利打开；
- B 平台里的内容，离开那个 App 之后就容易“变味”；
- 想分享给外部合作方，对方还得注册账号、下载软件，门槛一下就高了。

这跟我们想要的完全相反。

我们想要的是：像在微信里直接发一个 PDF 那样简单，对方点开就能看，看到的内容和我完全一致，不需要额外操作。

GitHub 做到了这一点。

你只需要分享一个链接，直接定位到目标文件，GitHub 就能自动渲染 Markdown、图片、PDF，甚至三维模型文件 `.stl`。点开即看，无需下载，也无需转换。

而且这个链接可以被反复引用：写进文档、贴进群里、嵌入自动化流程，都会很顺手。**一个链接复用率越高，团队协作效率就越高。**

#### 第二，我们选择“纯文本”，是为了让 AI 帮我们干活

在 AI 普及之前，我们生活和工作中交换的文件，绝大多数都是富文本格式，比如最常见的 `.docx`。

大家可能没想过，一个 `.docx` 文件里，每个字都可以带着自己的字体、字号、颜色，段落对齐、行距、页眉页脚这些信息也都会被记录下来。

视觉上当然更好看，但代价也很明显：

- **文件体积膨胀**，动不动就是几兆起步，发送前还得先压缩；
- **解析极其复杂**，需要专门的软件才能打开；
- **对 AI 极其不友好**——大语言模型处理一个 `.docx`，需要消耗更多 token，也要花更长时间才能“读懂”里面的内容。

而对计算机和 AI 来说，**最友好、最省力、处理速度最快的，始终是结构化数据和纯文本文档。**

所以，为了让我们以后能“更懒”一点，也就是少做格式转换、少压缩文件、少等 AI 慢慢解析，**我们选择纯文本作为团队的主要文档载体。**

> Markdown + GitHub，大致就是目前这个世界上**人类可读、机器可解析、AI 最省 token** 的组合之一。

#### 第三，也是最重要的：版本控制

最后，也是最核心的一点，**版本控制**。

用传统的网盘或共享文件夹，你的文件历史是这样的：

> `方案_最终版.docx` → `方案_最终版_v2.docx` → `方案_最终版_真的最终版.docx` → `方案_最终版_打死不改版.docx`

这叫“文件名版本控制”，本质上还是**人肉记忆**。

而 GitHub 的版本控制更像这样：

- 每一次修改，都会留下记录：**谁改的、什么时候改的、为什么改、改了哪些地方**；
- 想回到任何一个历史状态，点一下鼠标就行；
- 两个人同时改同一个文件时，Git 会帮你合并，而不是互相覆盖；
- 改错了也不用慌，随时可以回退。

**有了版本控制，你做的就不只是“写文档”，而是在积累团队的集体记忆。**

[Visual Studio Code](https://code.visualstudio.com/) 是一个非常好用的工具，接下来我们大概率会把它作为写文档、写代码、和 GitHub 交互的核心编辑器；如果你已经有熟悉的编辑器，也完全可以继续用自己顺手的工具。可以把 GitHub 理解成我们的“云端仓库”，而 VS Code 则是每个人手里的“本地工作台”。

1. Git 集成——和 GitHub 无缝衔接
2. Markdown 编辑体验极佳
3. 插件生态极其丰富
4. 轻量、快速、跨平台

另外，如果你主要编辑 `.md` 文件，Mac 用户我还比较推荐 [MarkEdit](https://github.com/MarkEdit-app/MarkEdit/releases/tag/v1.35.0)。它是 macOS 上一款免费、开源、极简的 Markdown 编辑器，安装包不到 4MB，启动速度也很快。

[docs](https://docs.github.com/zh) 是 GitHub 官方出品的简体中文版帮助文档，系统介绍了平台的核心功能与常用操作，是初学者快速上手时最权威的参考资料。
