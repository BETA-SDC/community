# 通知归档规范

中文 | [English](./message-archive-guidelines.md)

> 本文档说明正式通知、邮件、群消息和宣传文案发送后如何归档。完整活动流程见 [活动建立流程](./event-creation-workflow.zh.md)。

## 什么是通知归档

通知归档不是把草稿随便放进某个文件，而是在对应活动主 Issue 下创建 `[message]` 类型 Sub-issue，把已经实际发送的信息完整复制一份存档。

归档用于之后确认：

- 当时发送了什么
- 通过什么渠道发送
- 什么时候发送
- 由谁发送或负责
- 是否有截图、链接或收件范围说明

> [!IMPORTANT]
> 归档内容以实际发送后的最终版本为准。草稿可以在分支文件中协作，但正式发送后仍需要在 `[message]` Sub-issue 中保存最终发送内容。

## 什么时候需要归档

应该归档：

- 面向活动参与者的邮件通知
- 微信群、飞书群等正式群通知
- 报名开启、报名提醒、时间地点变更等重要消息
- 公众号、推文、招募文案等对外宣传内容
- 会影响活动安排、报名、到场或对外认知的正式信息

通常不需要归档：

- 群里的临时闲聊
- 未发送的草稿
- 只在协作者之间确认的小问题
- 已被正式归档版本替代的中间修改稿

## Sub-issue 标题

通知归档类 Sub-issue 使用：

```text
[message] 活动名称 - 渠道 - YYYY-MM-DD
```

示例：

```text
[message] Math Help Room - 邮件通知 - 2026-09-09
[message] Group Birthday Ceremony - 微信群通知 - 2026-09-16
```

标题里的活动名称应与活动主 Issue 保持一致。渠道写实际发送渠道，例如 `邮件通知`、`微信群通知`、`公众号推文`。

## Sub-issue 内容

归档 Sub-issue 至少包含：

- 已发送文案的完整内容
- 发送渠道
- 发送时间
- 发送人或负责人
- 截图、链接或收件范围说明，如适用

推荐结构：

```markdown
## 发送信息

- 渠道：
- 发送时间：
- 发送人：
- 收件范围：

## 正文

在这里复制最终发送的完整内容。

## 附件或说明

- 截图：
- 链接：
- 其他说明：
```

## 标签

通知归档 Sub-issue 至少添加 `message` 标签。

按渠道可追加：

- 邮件：`message` + `mail`
- 群通知：`message` + `group-notice`

如果归档过程同时暴露出后续任务，例如需要补发、改海报或更新报名表，应另开 `[task]` Sub-issue，不要把任务讨论混在归档记录里。
